## ❓ Part 1 — Why Monitoring Is Essential

```
Single cluster, manual checks:
  → Feasible. One team, one environment, few moving parts.

Multiple environments (Dev, Staging, Production):
  → Manual monitoring becomes unsustainable
  → No single person can eyeball dashboards across every cluster,
    every service, every deployment, all the time
```

```
What proactive monitoring actually buys you:
  → Deployment health visibility (did the rollout actually succeed?)
  → Service availability tracking (is this actually reachable right now?)
  → Resource utilization insight (CPU/memory pressure before it becomes an outage)
  → Catching problems BEFORE users report them, not after
```

> **The core shift:** monitoring moves an org from reactive firefighting ("a user reported the app is down") to proactive detection ("an alert fired five minutes before anyone would have noticed").

## 🏗️ Part 2 — Architecture Overview

```
                    ┌─────────────────────┐
                    │  Kubernetes API      │
                    │  Server (metrics)    │
                    └──────────┬───────────┘
                               │ scrapes
                               ▼
                    ┌─────────────────────┐
                    │   Prometheus Server  │
                    │  (Time Series DB,    │
                    │   stored on disk)    │
                    └──────────┬───────────┘
                     │                    │
          alerts on  │                    │ queried by
          conditions ▼                    ▼
                ┌───────────┐      ┌──────────────┐
                │Alertmanager│      │   Grafana     │
                │  (Slack,   │      │ (dashboards,  │
                │   Email)   │      │ visualization)│
                └───────────┘      └──────────────┘
```

| Component | Role |
|---|---|
| **Prometheus Server** | Scrapes metrics from the Kubernetes API Server (and other targets), stores them in a built-in Time Series Database on disk |
| **Alertmanager** | Watches Prometheus for conditions (e.g. API server downtime) and routes notifications to Slack, Email, etc. |
| **Grafana** | Connects to Prometheus as a data source and turns raw time-series metrics into readable, shareable dashboards |

> **Why this separation matters:** Prometheus focuses purely on collection and storage; Alertmanager focuses purely on notification routing; Grafana focuses purely on visualization. Each piece can be swapped or scaled independently.

## 🛠️ Part 3 — Implementation & Setup

### Environment

```bash
# Minikube with hyperkit driver — chosen for better networking behavior
# on this setup compared to the default driver
minikube start --driver=hyperkit
```

### Installing Prometheus via Helm

```bash
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update

helm install prometheus prometheus-community/kube-prometheus-stack \
  --namespace monitoring --create-namespace
```

```bash
kubectl get pods -n monitoring
# Prometheus, Alertmanager, and related components come up here
```

### Installing Grafana via Helm

```bash
# In many kube-prometheus-stack installs, Grafana is bundled in automatically.
# If installing standalone:
helm repo add grafana https://grafana.github.io/helm-charts
helm install grafana grafana/grafana --namespace monitoring
```

### Retrieving the Autogenerated Grafana Login

```bash
kubectl get secret grafana -n monitoring \
  -o jsonpath="{.data.admin-password}" | base64 --decode
```

```bash
kubectl port-forward -n monitoring svc/grafana 3000:80
# Access Grafana at http://localhost:3000
# Login: admin / <decoded password from above>
```

### Importing a Pre-Built Community Dashboard

```
Instead of building dashboards from scratch:
  Grafana UI → Dashboards → Import → Enter Dashboard ID: 3662
  → Loads a pre-configured, community-maintained
    Kubernetes cluster monitoring dashboard instantly
```

> **Why this matters practically:** dashboard design (panel layout, useful queries, thresholds) is its own skill — reusing a battle-tested community dashboard gets a fully functional view of the cluster running in minutes instead of hours of manual PromQL query-writing.

## 📊 Part 4 — Advanced Monitoring: Kube State Metrics

### The Gap in Raw API Server Metrics

```
Kubernetes API Server metrics alone are fairly limited —
mostly request counts, latencies, and basic health signals.

They do NOT deeply expose the STATE of higher-level objects like:
  → Deployments (desired replicas vs. available replicas)
  → Pods (phase, restart counts, readiness)
  → ReplicaSets (current vs. desired counts)
```

### What Kube State Metrics Adds

```
Kube State Metrics is a separate service that:
  → Watches the Kubernetes API
  → Generates metrics describing the STATE of objects,
    not just raw resource usage

Example insights it enables:
  "Desired replicas: 5, Available replicas: 3"
    → Immediately visible as a dashboard panel or alert,
      instead of requiring someone to run `kubectl get deployment`
      and notice the mismatch manually
```

> **Why this is crucial:** it directly answers "does the current state of my resources match the desired configuration?" — which is really the core reconciliation question that Kubernetes itself is built around, now made visible and alertable.

## 🎯 Part 5 — Custom Application Monitoring

```
Standard cluster metrics + Kube State Metrics only cover
infrastructure and orchestration health.

For visibility into an application's OWN internal behavior
(request latency, business logic errors, queue depth, etc.),
the application itself needs to expose metrics.
```

### The Path to Custom Metrics

```
1. Instrument the application using a Prometheus client library
   (available for most languages: Python, Go, Java, Node.js, etc.)

2. Application exposes a /metrics HTTP endpoint
   → Returns metrics in Prometheus's plain-text exposition format

3. Update the Prometheus ConfigMap (scrape_configs)
   → Add the new target so Prometheus starts scraping
     the application's /metrics endpoint on its own schedule

4. Metrics now appear in Prometheus/Grafana alongside
   cluster-level and Kube State metrics
```

> **The layered approach recommended in the session:** start with standard cluster metrics (Prometheus + API Server) → layer on Kube State Metrics for orchestration-level health → finally add custom application metrics for granular, business-specific observability. Skipping straight to custom app metrics without the foundational layers leaves infrastructure-level blind spots.

## 📖 Key Terms

| Term | What it means |
|---|---|
| **Prometheus** | Open-source monitoring system that scrapes and stores metrics as time series |
| **Time Series Database** | A database optimized for timestamped data points — Prometheus's native storage model |
| **Alertmanager** | Component that routes alerts from Prometheus to channels like Slack or Email based on defined conditions |
| **Grafana** | Visualization layer that queries Prometheus (or other data sources) to build dashboards |
| **Helm Chart** | Packaged Kubernetes configuration used here to install Prometheus and Grafana cleanly |
| **Dashboard ID 3662** | A popular community-maintained Grafana dashboard ID for general Kubernetes cluster monitoring |
| **Kube State Metrics** | A service exposing detailed state metrics (Deployments, Pods, ReplicaSets) beyond what the raw API Server exposes |
| **`/metrics` Endpoint** | A standard HTTP endpoint apps expose (via Prometheus client libraries) so Prometheus can scrape their internal metrics |
| **Prometheus Client Library** | Language-specific libraries used to instrument an application and expose custom metrics |
| **Scrape Config** | The Prometheus configuration section defining which targets to pull metrics from and how often |

## 💡 My Takeaway

The layered framing at the end tied the whole session together well: standard Prometheus metrics tell you the cluster's infrastructure is alive, Kube State Metrics tells you whether the *desired* state actually matches *reality* for your workloads, and custom app metrics tell you whether the application is actually doing its job correctly from a business-logic standpoint. Each layer answers a genuinely different question, and skipping straight to custom metrics without the first two would mean flying blind on basic orchestration health.

Retrieving the Grafana password from a Kubernetes Secret rather than a hardcoded default was a nice small reinforcement of yesterday's ConfigMaps/Secrets session — seeing Secrets actually used this way in a real Helm-installed tool, rather than just in an isolated example, made that concept feel more concrete. Importing dashboard `3662` instead of building one from zero was also a good practical reminder: for infrastructure tooling, there's real efficiency in trusting a widely-used community artifact over reinventing something that hundreds of other engineers have already tuned.
